# چند سال مالی هم‌زمان و افتتاحیه (راهنمای فارسی)

نسخهٔ پکیج: **۱۳.۸.۰**

این راهنما برای تیم محصول و توسعه‌دهندهٔ اپ مصرف‌کننده نوشته شده است.
هدفش این است که بفهمید در کسب‌وکار واقعی (خصوصاً وقتی ادارهٔ مالیات چند ماه بعد گزارش می‌خواهد) چطور با سال مالی و سند اول دوره کار کنید.

---

## مشکل بیزینسی چه بود؟

در خیلی از کسب‌وکارها:

1. سال مالی مثلاً از ۱ فروردین تا ۲۹ اسفند است.
2. فروش و انبار از روز اول سال جدید باید کار کنند و سند `posted` بزنند.
3. حسابدار تا چند ماه بعد هنوز در حال بررسی و اصلاح سال قبل است.
4. افتتاحیهٔ سال جدید باید از ماندهٔ نهایی سال قبل بیاید؛ پس تا بسته شدن سال قبل، افتتاحیه نباید «قطعی نهایی» شود.

قبلاً پکیج تقریباً این فرض را داشت:

- فقط یک سال `active`
- افتتاحیه فقط قبل از اسناد عملیاتی
- `carryForward` فقط از سال `closed`

این فرض برای go-live و مالیات ایران سخت بود. از ۱۳.۸.۰ این الگو با کانفیگ پشتیبانی می‌شود.

---

## سه مفهوم را قاطی نکنید

| مفهوم | معنی ساده |
|--------|-----------|
| `active` | سال باز است؛ می‌توان در آن سند زد |
| `is_current` | سال پیش‌فرض UI / انتخاب پیش‌فرض اپ |
| `closed` | سال قفل شده؛ دیگر ثبت جدید نمی‌پذیرد |

مثال:

- سال ۱۴۰۳ هنوز `active` است (حسابدار اصلاح می‌کند)
- سال ۱۴۰۴ هم `active` است و `is_current = true` (فروش روی همین کار می‌کند)
- وقتی سند با تاریخ داخل ۱۴۰۳ می‌زنید، پکیج از روی **تاریخ سند** سال را پیدا می‌کند، نه از روی `current()`

---

## کانفیگ‌های جدید

در `config/accounting.php`:

### `fiscal_year.allow_multiple_active` (پیش‌فرض: `true`)

اگر `true` باشد، چند سال می‌توانند هم‌زمان `active` باشند.
فعال‌سازی سال جدید، سال قبل را نمی‌بندد؛ فقط `is_current` را روی سال جدید می‌گذارد.

اگر `false` باشد، رفتار قدیمی برمی‌گردد: تا سال قبل را نبندید، سال جدید activate نمی‌شود.

### `opening.allow_after_posted_activity` (پیش‌فرض: `true`)

اگر `true` باشد، حتی بعد از فروش/خرید `posted` هم می‌توانید افتتاحیه را `confirm` کنید.

اگر `false` باشد، رفتار سخت‌گیرانهٔ قبلی می‌ماند.

### `opening.require_prior_year_closed_for_confirm` (پیش‌فرض: `true`)

اگر `true` باشد، تا وقتی سال متوالی قبلی وجود دارد و هنوز `closed` نشده، نمی‌توانید:

- `confirm()` / `post()` افتتاحیه
- یا `completeOpening()`

را برای سال جدید نهایی کنید.

این همان قفل بیزینسی مهم است: افتتاحیهٔ سال جدید تا بسته شدن سال قبل، نهایی نمی‌شود.

### `opening.allow_provisional_carry_forward` (پیش‌فرض: `true`)

اگر `true` باشد، می‌توانید از سال قبلی که هنوز `active` است `carryForward` بگیرید.
نتیجه فقط پیش‌نویس (`draft`) است و در `meta.provisional = true` علامت می‌خورد.
با هر بار اجرای دوباره، پیش‌نویس‌ها با ماندهٔ فعلی مبدأ به‌روز می‌شوند.

قطعی کردن همچنان منتظر بسته شدن سال قبل می‌ماند (اگر کانفیگ بالا `true` باشد).

## جریان پیشنهادی برای اپ شما

```text
۱) سال جدید را activate کنید
   → سال قبل می‌تواند هنوز active بماند
   → سال جدید is_current می‌شود

۲) فروش/انبار روی تاریخ‌های سال جدید سند posted بزنند
   → مشکلی نیست

۳) (اختیاری) carryForward موقت از سال قبلِ هنوزباز
   → فقط draft افتتاحیه در سال جدید
   → حسابدار می‌تواند ببیند و ویرایش کند

۴) حسابدار تا چند ماه روی سال قبل سند اصلاحی می‌زند
   → هر وقت خواستید دوباره carryForward بزنید تا draft رفرش شود

۵) بستن سود و زیان سال قبل → close سال قبل

۶) یک بار دیگر carryForward نهایی (الان مبدأ closed است)
   → meta.provisional = false

۷) confirm افتتاحیهٔ هر شعبه در سال جدید
   → حالا opening_done می‌تواند true شود
```

### کد نمونه

```php
use Karnoweb\Accounting\Facades\Accounting;

// سال قبل هنوز باز است؛ سال جدید را فعال می‌کنیم
$fyNew = Accounting::fiscalYear()->activate($fyNewDraft);

// فروش با تاریخ داخل سال جدید — resolve از روی date
Accounting::document()
    ->type('sale')
    ->date('2026-01-20')
    // ...
    ->post();

// انتقال موقت مانده (پیش‌نویس)
$drafts = Accounting::opening()->carryForward($fyOld, $fyNew);

// ... اصلاحات روی سال قبل ...

Accounting::closing()->closeProfitAndLoss($fyOld);
Accounting::fiscalYear()->close($fyOld);

// انتقال نهایی و تأیید
$drafts = Accounting::opening()->carryForward($fyOld, $fyNew);
foreach ($drafts as $draft) {
    Accounting::opening()->confirm($fyNew, $draft->branch_id);
}
```

### عوض کردن سال پیش‌فرض UI

```php
Accounting::fiscalYear()->setCurrent($fyOld); // فقط برای UI/default
// یا:
$fyOld->setCurrent();
```

بستن سالِ جاری (`is_current`) اگر سال active دیگری مانده باشد، خودکار همان را `is_current` می‌کند (معمولاً جدیدترین `start_date`).

## ثبت سند و تشخیص سال مالی

ترتیب resolve در ساخت سند:

1. اگر `fiscal_year_id` صریح داده شده → همان
2. اگر تاریخ دارد و `auto_detect` روشن است → `findByDate(date)`
3. اگر تاریخی نیست → `current()` به‌عنوان آخرین پناه

نکتهٔ مهم: اگر تاریخ داده‌اید ولی هیچ سالی آن را پوشش نمی‌دهد، دیگر بی‌صدا به `current()` برنمی‌گردد؛ خطا می‌دهد (`no_fiscal_year_for_date`).
این برای حالت چندسال هم‌زمان ضروری است تا سند سال قبل اشتباهاً داخل سال جدید نرود.

`PostingService::assertAllowed()` از قبل هم فقط با `findByDate` کار می‌کرد و به `current()` متکی نبود.

## افتتاحیه خالی / ناقص

- می‌توانید از اول سال `saveDraft` داشته باشید (حتی نامتوازن).
- پیش‌نویس روی دفتر اثر ندارد.
- قطعی کردن (`confirm`) وقتی معنی دارد که ردیف‌ها متوازن باشند.
- سند `posted` خالی نداریم و نباید داشته باشیم؛ مدل اسناد شما immutable است.
- اگر بعد از confirm خواستید عوض کنید: `void` → `saveDraft` → `confirm`.

با `allow_after_posted_activity=true`، قطعی کردن وسط/اواخر سال از نظر پکیج مجاز است؛
ولی با `require_prior_year_closed_for_confirm=true`، تا بسته شدن سال قبل نهایی نمی‌شود.

---

## چه چیزی عمداً عوض نشده؟

- بستن سود و زیان هنوز سند `closing` می‌سازد و سال را خودش `closed` نمی‌کند.
- `FiscalYearService::close()` هنوز سند نمی‌سازد؛ فقط قفل سال است.
- اختتامیه در طول سال «آپدیت شونده» نیست؛ برای بستن دوباره باید void و اجرای مجدد.
- بازهٔ سال‌ها هنوز به‌طور پیش‌فرض هم‌پوشانی تاریخی ندارند (`allow_overlap=false`).

---

## چک‌لیست برای اپ مصرف‌کننده

- [ ] در UI، سال پیش‌فرض را از `is_current` بگیرید؛ لیست سال‌های باز را جدا نشان دهید.
- [ ] تاریخ سند را همیشه بفرستید تا resolve درست کار کند.
- [ ] `confirm` افتتاحیه را به نقش حسابدار و بعد از `close` سال قبل محدود کنید.
- [ ] اگر `carryForward` خودکار می‌زنید، فقط draft بسازید؛ auto-confirm نکنید مگر سال قبل بسته باشد.
- [ ] برای سال اول سیستم (بدون سال قبلی)، `require_prior_year...` مانع نیست چون سال قبلی وجود ندارد.

## پیام‌های خطای مرتبط

| کلید | معنی ساده |
|------|-----------|
| `fiscal_year_another_active` | چندسال هم‌زمان خاموش است |
| `opening_has_posted_activity` | بعد از عملیات، افتتاحیه ممنوع است (وقتی کانفیگ سخت‌گیر باشد) |
| `opening_prior_year_not_closed` | اول سال قبل را ببند، بعد افتتاحیه را قطعی کن |
| `opening_source_not_closed` | مبدأ carry هنوز برای انتقال مجاز نیست |
| `no_fiscal_year_for_date` | این تاریخ داخل هیچ سال مالی‌ای نیست |
