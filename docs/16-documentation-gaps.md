# وضعیت مستندات و شکاف‌های شناسایی‌شده

این فایل مواردی را ثبت می‌کند که یا:

- در کد قابل تشخیص قطعی نبودند
- بین مستندات قدیمی و کد اختلاف داشتند
- نیازمند تصمیم محصول/تیم هستند

## ۱. مواردی که از روی کد **قطعی** شد

این موارد در مستندات قدیمی مبهم یا نادرست بودند، اما از روی کد تعیین شدند:

- نسخه فعلی پکیج `13.4.1` است.
- پکیج برای `PHP ^8.3` و `Laravel ^13.0` تنظیم شده است.
- `Branch` ماژول کامل پکیج نیست؛ فقط `branch_id` ذخیره می‌شود.
- `CostCenter` روی `DocumentItem` وجود دارد، اما گزارش‌های اصلی فعلاً فیلتر مستقل بر اساس آن ندارند.
- `void` و `reversal` دو رفتار متفاوت هستند.
- `FiscalYearService::close()` سند اختتامیه نمی‌سازد.
- `ClosingService` سود و زیان را می‌بندد، اما سال مالی را `closed` نمی‌کند.

## ۲. شکاف‌های اجرایی یا قراردادی

### ۲.۱ `accounting.document.allowed_types`

این کلید در config وجود دارد، اما در کد فعلی اعتبارسنجی سخت‌گیرانه‌ای روی آن دیده نمی‌شود.  
در نتیجه:

- این فهرست امروز بیشتر یک **قرارداد پیکربندی** است
- نه یک **enforcement کامل در application layer**

اگر تیم بخواهد این فهرست نقش کنترلی داشته باشد، باید صریحاً در `DocumentService` enforce شود.

### ۲.۲ `accounting.document.workflow_enabled`

این کلید در config وجود دارد، اما در بررسی کد هسته استفاده مؤثری از آن پیدا نشد.  
وضعیت‌های `pending` و `approved` وجود دارند، اما workflow کامل قابل‌پیکربندی در هسته فعلی دیده نشد.

### ۲.۳ `accounting.enabled`

این کلید در config وجود دارد، اما در رفتار سرویس‌های اصلی استفاده عملی مشخصی از آن دیده نشد.

### ۲.۴ `reports.per_page`

در config وجود دارد، اما گزارش‌های هسته‌ای DTO-based هستند و صفحه‌بندی داخلی بر پایه این کلید در کد فعلی دیده نشد.

## ۳. قابلیت‌هایی که **در پکیج نیستند** اما ممکن است از روی مثال‌ها اشتباه برداشت شوند

این موارد نباید به‌عنوان قابلیت هسته معرفی شوند:

- ماژول مستقل صندوق
- ماژول مستقل بانک
- انتقال وجه بانکی با موجودیت اختصاصی
- مشتری / فروشنده / اشخاص به‌عنوان ماژول داخلی
- کالا / خدمت / انبار
- مالیات
- ارز
- UI گزارش‌ها
- صورت سود و زیان نهایی
- ترازنامه
- صورت جریان وجه نقد
- بازگشایی سال مالی بسته
- اصلاح بین‌سال‌ها
- برگشت جزئی سند

## ۴. مثال‌های فروشگاهی

پوشه `docs/examples/shop/` سناریوهای دامنه فروشگاهی را شامل می‌شود، اما بخشی از آن‌ها به منطق اپلیکیشن مصرف‌کننده وابسته‌اند و نه به هسته پکیج.

برای استفاده بلندمدت:

- این مثال‌ها باید «نمونه‌های مفهومی» تلقی شوند
- نه «قرارداد رفتاری هسته»

اگر تیم بخواهد این مثال‌ها مرجع رسمی بمانند، لازم است برای هر سناریو مشخص شود:

1. کدام بخش توسط خود پکیج پشتیبانی می‌شود
2. کدام بخش نیازمند لایه اپلیکیشن مصرف‌کننده است

## ۵. پیشنهادهای بعدی برای تکمیل مستندات

1. بازبینی و پالایش فایل‌های قدیمی که هنوز مثال یا API منسوخ دارند
2. تفکیک روشن مثال‌های «هسته پکیج» از مثال‌های «دامنه فروشگاهی»
3. افزودن یک سند جدا برای «تغییرات حساس بر گزارش‌ها»
4. افزودن تست/مستند برای رفتار مورد انتظار `allowed_types` و `workflow_enabled` در صورت تصمیم تیم
